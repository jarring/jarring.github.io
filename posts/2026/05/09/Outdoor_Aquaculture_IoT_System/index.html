Outdoor Aquaculture IoT System — Architecture Design Document & Technical Validation

A technical design and ADR document for a large-scale aquaculture IoT system (3000–5000 ponds), covering MQTT edge architecture, edge autonomy under 4G instability, message storm defense, time-series storage, and multi-tenant isolation.

1. Background & Constraints

1.1 Business Scenario

The core risk in outdoor aquaculture (shrimp, fish) is the nighttime sudden drop in dissolved oxygen leading to floating-head / pond-turnover events. The window for dissolved oxygen (DO) to fall from the safe value (>5 mg/L) to the danger value (<2 mg/L) is only 15–30 minutes. Once triggered, the farmer must complete operations such as starting or stopping aerators and adjusting water levels within an extremely short time.

Protocol Advantages Disadvantages POC conclusion

3. Core Architecture Decisions (ADR)

ADR-001: Edge Autonomy vs. Cloud-Centralized Control

Dimension Option A: Edge autonomy Option B: Cloud-centralized
Usable while offline ✔ Local closed loop, no network dependency ❌ Offline = loss of control
Response latency <100 ms (local compute) 500 ms–2 s (incl. network round trip)
Rule updates Delivered via OTA Take effect instantly
Complexity Edge logic complex; dual-end consistency required Logic centralized, simple
Troubleshooting Distributed logs; hard to locate Centralized logs; easy to diagnose

Conclusion: Choose Option A (edge autonomy as primary + cloud-side policy delivery). Rationale: under a 15–30-minute floating-head window, cloud round-trip latency is unacceptable; at 15%–30% packet loss, cloud control is unreliable. An edge node must independently complete the full local loop of threshold judgment → alert → linked control when offline.

ADR-002: MQTT Broker Selection

Dimension EMQX Mosquitto HiveMQ
Clustering ✔ Native clustering ❌ Primarily single-node ✔ Enterprise clustering
Connections per node 1,000,000 (official benchmark) ~10,000 500,000
Rules engine ✔ Built-in SQL rules ❌ Requires external component ✔
Authorization/authentication ✔ Rich Basic ✔
Open-source license Apache 2.0 EPL/EDL Commercial
Community activity High High Medium

Conclusion: Choose EMQX Open Source. Rationale: native clustering is a hard requirement for 1,000+ edge-node connections; the built-in rules engine reduces middleware development; Apache 2.0 carries no commercial risk. The POC phase uses Mosquitto for quick validation, then switches to EMQX for production.

ADR-003: Time-Series Data-Store Selection

Dimension InfluxDB TimescaleDB TDengine
Write throughput High Medium-high Extremely high (officially claims 20× InfluxDB)
Compression ratio ~10:1 ~5:1 ~10:1
Query language InfluxQL / Flux SQL SQL-like
Clustering 2.0+ open-source single node; clustering commercial Open source Open source (3.0+)
Ecosystem maturity Extremely high High (PostgreSQL ecosystem) Medium
Hardware footprint Medium High (PG overhead) Low

Conclusion: Choose TDengine Community Edition. Rationale: extreme write throughput suits high-frequency sensor data (3,500 ponds × multiple metrics); high compression ratio reduces storage cost; open-source clustering in 3.0+; SQL-like lowers the learning curve. If the team has deep PostgreSQL experience, TimescaleDB can be chosen to reduce migration cost.

ADR-004: Edge-Computing Hardware Platform

Dimension Raspberry Pi 4B NVIDIA Jetson Nano ESP32 + gateway
Power 3–5 W 5–10 W <1 W (ESP32) + 2 W (gateway)
Video AI Feasible (YOLOv5s 1 fps) Feasible (10+ fps) ❌
Unit price ~¥400 ~¥1,500 ~¥50 + ~¥200
Industrial temp. range 0–50 °C -25–80 °C (industrial version) -40–85 °C
Storage reliability microSD (fragile) eMMC Flash
Multi-sensor expansion 8+ USB/GPIO Rich Limited

Conclusion: Choose an ESP32 + edge-gateway layered architecture. Rationale: when a single pond does not require video AI, the ESP32 directly acquires sensor data + controls the aerator (<1 W, solar-friendly); inference-capable gateways are deployed only at ponds that need video AI (est. 20%–30%). The layered design lowers overall BOM cost and avoids the waste of “equipping every pond with a Raspberry Pi.”

ADR-005: Offline-Autonomy Strategy

Dimension Periodic reporting + local rules Pure event-driven Dual-channel redundancy
Bandwidth usage Medium (periodic heartbeat + data) Extremely low High
Offline safety ✔ Local rules closed loop ⚠️ Rules are simple ✔
Implementation complexity Medium Low High
Power Medium Low High
Cloud-recovery awareness ✔ Heartbeat timeout detection ❌ ✔

Conclusion: Choose periodic reporting + local rules + 4G/LoRa dual-channel redundancy (for critical ponds). Normal mode: report every 5 min + local threshold monitoring; alert mode: switch to 30-s high-frequency reporting; when offline: full local autonomy (threshold judgment → audible/visual alarm → linked aerator); after the network recovers, backfill data. Critical ponds (high-density farming) add a LoRa backup channel to neighbor nodes.

ADR-006: Client Real-Time Communication

Dimension WebSocket MQTT over WS Server-Sent Events
Bidirectional ✔ ✔ ❌ (one-way)
Native browser support ✔ Requires a library ✔
Reconnection Must be built in-house ✔ Protocol-level support ✔ Automatic
Message overhead Minimal Slightly larger (MQTT header) Small
Multi-end adaptation ✔ ✔ ✔

Conclusion: Choose MQTT over WebSocket. Rationale: unified with the device-side protocol, reducing end-to-end complexity; the client reuses the MQTT topic-subscription model, with permission control consistent with the device side; EMQX natively supports WS access.

5.2 Message-Storm Mitigation

Problem Statement

Thunderstorm evenings are a high-incidence window for sudden DO drops / floating-head events. 3000+ ponds may trigger alerts in the same time window, creating a concurrent-message peak.

Quantitative estimate (3,000-pond concurrent-alert scenario):

Dimension Value Note
Alert-window messages per pond ~80 P0/P1/P2 alerts + heartbeats + state changes
Total message count ~240,000 3,000 × 80
Duration 15–30 min Floating-head response window
Average message rate 133–267 msg/s Uniform assumption
Burst peak (first minute) ~3,000 msg/s (entire cluster) First batch of 3,000 ponds’ P2 arrives simultaneously
Per node (3-node cluster) ~1,000 msg/s Sharded by connection hash

Throughput conclusion: At message rates below 4,000 msg/s, neither the EMQX cluster nor TDengine writes are in the bottleneck zone. The real pressure points are:

  1. External-notification channels (SMS / push) delivery latency — not system throughput
  2. End-to-end latency: alert generated → farmer receives notification → response action must complete within the 15–30-minute window
  3. Control-plane cascading: farmers’ panic-driven remote operations (repeatedly toggling aerators) amplify message volume

Design Principles

The first rule of an alert system is “don’t lose,” not “don’t crash.”

❌ Don’t ✔ Do
Circuit-break and drop alert messages Store everything; push notifications can be merged
Sacrifice P2/P3 when the system is overloaded P0/P1 delivered first; P2/P3 merged and pushed
Cloud as the sole path for alert execution Edge local autonomy is the life-saving channel
Leave the control plane unlimited Rate-limit farmer operations to prevent panic amplification

Detailed Parameters by Layer

L1: Edge local autonomy

Parameter Value Note
Trigger condition DO < 3 mg/L for 2 min No cloud judgment required
Actions Start aerator + audible/visual alarm Local relay / IO control
Independent notification Built-in SIM SMS / call on device Does not pass through cloud aggregation gateway
4G packet-loss tolerance Still self-rescues at 100% loss Edge rules pre-installed

Core logic: No matter how large the cloud-side message storm, the fish in the pond have already been saved by the local rules. Whether the cloud notification is delayed by 30 s or 5 s only changes “whether the farmer knows,” not “whether the fish die.”

L2: Cloud message classification and merging

Level Definition Push strategy Store Example
P0-Fatal DO < 2 mg/L Guaranteed: priority queue, unlimited retries, multi-channel (push + SMS + voice) ✔ All Floating-head risk
P1-Severe DO < 3 mg/L sustained Merge: 1 per pond per 5 min; full record in background ✔ All Intervention needed
P2-Warning DO < 4 mg/L Merge: 1 per pond per 15 min ✔ All Trend warning
P3-Info Normal fluctuation No real-time push; periodic digest ✔ All Daily fluctuation

Merging rules (no messages lost):

  • Merging affects only push frequency; all original alerts are fully written to TDengine
  • When the client opens the app, it pulls the complete timeline from history
  • When a new alert arrives within the merge window, the existing push card is updated (count +1) instead of showing a new notification

L3: External notification channels

SMS aggregation gateway design:

Parameter Value Note
Number of vendors ≥3 Aliyun / Tencent Cloud / Huawei Cloud + carrier direct connect
Per-channel capacity 200–500 msg/s Actual capacity for notification-class SMS
Aggregated multi-channel capacity 2000+ msg/s Parallel distribution
3,000 P0 delivery latency <5 s (normal) / <30 s (failover) End-to-end
Routing strategy Allocated by number segment (China Mobile / Unicom / Telecom / Broadnet) Improves delivery rate
Primary/backup switching 3 consecutive failures or failure rate >10% Auto-switch to backup channel
Idempotency control No duplicate within 30 s for same (eventId, phone) Prevents resend storm
P0 voice call Independent channel; auto-triggered 10 s after SMS failure Last resort

App push merging:

  • For the same pond at the same alert level, the client shows only 1 notification per minute
  • Notification content updates dynamically: "Pond A DO remains low (3/5 alerts)"
  • When vendor push channels are throttled, rely on the in-app WS long connection as a supplement

L4: Control-plane rate limiting

Operation type Rate-limit rule Purpose
Single-device control (aerator toggle) 1 per 30 s, max 3/min Prevent repeated clicks causing command storms
Batch operation (one-tap all-on) 1 per 5 min, requires confirmation Prevent panic all-on operations
Parameter change (alert threshold) 1 per min Prevent accidental touches
WS command dispatch 10 cmd/s per connection Protect edge-device processing threads

Why limit the control plane rather than the alert plane:

  • Alert messages = read-only notifications; losing them affects safety
  • Control commands = write operations; one extra message means one extra device action
  • A farmer frantically tapping “turn on aerator” 5 times on the app = the edge receives 5 commands = unnecessary state switches and ack messages

Comparison with the “Circuit Breaker” Approach

Dimension Circuit-breaker approach (❌ deprecated) This approach (✔ adopted)
Alert messages Drops P2/P3 when overloaded Store everything; push merging
System protection Sacrifice messages to protect the system Limit control plane + edge autonomy; don’t lose messages
Farmer experience Misses warning trends, jumps straight to P0 Receives the merged, complete alert timeline
Applicable scenario Generic internet high concurrency IoT scenarios where alert integrity is paramount
Extreme case Fish float to the surface unnoticed during the break Edge has already started the aerator; cloud delay only affects the notification

1,000+ persistent edge-node MQTT connections + 2,000+ farmer-client WS connections + O&M/admin-backend connections = 3,000+ long connections per cluster. During peak periods (thunderstorms), simultaneous online rate of clients jumps from 30% to 80%+.

5.5 Cost Control

Problem Statement

The largest hidden costs in an IoT project are communication fees + cloud-resource fees + O&M labor. At a scale of 3,500 ponds, saving ¥1/node/month = ¥42,000/year.

Solution Design

Three-tier edgetiers + bandwidth optimization:

Edge tierr Applicable scenario Configuration Target unit price
L1 Basic Small pond (<5 mu) ESP32 + 2 sensors <¥200
L2 Standard Medium pond (5–15 mu) ESP32 + 4–6 sensors + aerator control ¥200–400
L3 AI Large pond (>15 mu) Edge gateway + video AI + LoRa backup ¥500–800

Bandwidth-optimization strategies:

Strategy Savings ratio Implementation
Binary encoding (CBOR instead of JSON) ~60% 12 bytes → 5 bytes/reading
Delta reporting (report changes only) ~40% Identical consecutive values not reported
Local cache + batch upload ~30% Cache while offline; compressed batch send after recovery
Video uploads keyframe thumbnails only ~95% Upload 5 thumbnail frames on anomaly

Note: The goal of bandwidth optimization is to reduce long-term operating costs, not to handle message storms. Under message storms, the system relies on the four-layer defense in section 5.2 (edge autonomy + push merging + multi-channel notifications + control-plane rate limiting), without sacrificing alert messages.

Cloud-resource estimate (1,000 households / 3,500 ponds):

Resource Spec Quantity Monthly cost estimate
EMQX cluster 8C16G 3 nodes ~¥3,000
TDengine 16C32G + 2 TB SSD 3 nodes ~¥5,000
Business services 4C8G 6 instances ~¥4,000
Redis 4C8G 2 nodes ~¥1,500
Object storage 500 GB — ~¥500
4G IoT cards 10 MB/month/card 3,500 cards ~¥3,500
Total ~¥17,500/month

For comparison: if all control were cloud-based (reporting every 5 s), the 4G traffic cost would reach ~¥60,000/month — the edge-autonomy + low-frequency-reporting approach saves 70%+ in communication costs.

8.3 Key Architectural Insights

  1. In agricultural IoT, the primary risk is not the algorithm but the infrastructure: 4G signal, power, waterproofing, temperature — these “unglamorous” constraintsdetermine whether the system can survive
  2. The validation order should be reversed: first go to the pond to measure 4G signal, solar endurance, and sensor drift in dirty water; then polish the client UI
  3. Edge autonomy is not a feature — it is a survival capability: whether the system can close the loop independently after a pond goes offline takes priority over any interaction experience
  4. The reusable value of architectural decisions outweighs point solutions: once selection comparisons, threshold derivations, and scaling parameters are documented, they can serve directly as a baseline for implementation
