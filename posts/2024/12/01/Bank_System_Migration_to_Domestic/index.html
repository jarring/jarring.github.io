Bank System Migration to Domestic Tech Stack: From CentOS Retirement to Internal Cloud Go-Live

Dec 1 2024 TechLeadership 25 minutes read (About 3815 words)

A practical walkthrough of a banking system migration under China’s XinChuang initiative—moving from CentOS to an internal cloud while coordinating Oracle Data Guard, Elasticsearch-to-OpenSearch transition, microservice containerization, and 14 external system interface changes, all within a single coordinated cutover window.

1. Background and Challenges

Once the bank’s domestic technology (xinchuang) mandate was issued, all existing CentOS physical servers had to be decommissioned within the prescribed timeframe. At the same time, the bank’s architecture department made it clear: new servers should be provisioned on the internal cloud platform whenever possible. This meant we were not facing a simple “lift and shift” — it was a full-stack migration spanning the database, the search layer, the microservices, and external interfaces.

Core constraints:

  • Database: Oracle → Oracle. Because of the data volume and the need for transactional consistency, it stayed on physical machines below the cloud boundary.
  • Search layer: Elasticsearch → OpenSearch, replaced together with the domestic tech migration.
  • Microservices: migrated in full to the internal cloud.
  • External interfaces: the IP address changed after migration, affecting a large number of external systems.

2. Migration Overview and Layered Strategy

Faced with four different layers to migrate, the overall thinking was: let the test environment pave the way first, validate that the approach works, then push the production migration forward layer by layer according to risk level and data flow, with each layer independently rollbackable.

Core Principles

Test environment first: containerization, the configuration center, and network policies were all validated in the test environment first, confirming there were no hidden traps before production migration began.

Every layer has an independent rollback path: the database has its old primary/standby, ES has the source cluster, microservices have the old instances, and external interfaces have a per-system fallback plan.

Layers are decoupled by interfaces: microservices keep running while the database and ES are switched over; external interfaces are not affected while microservices are switched — until the final unified window.

Coordination work is front-loaded: the approval process for external interfaces is long, so it starts on day one of the project, not after the technology is ready.

Execution Order

  1. Microservice containerization and integration testing in the test environment — done first, to validate that containerization works, the configuration center is usable, and read/write connectivity to the database and search layer is sound. No production environment touched.
  2. Database migration — once the test environment is validated, the production database RMAN + DG migration begins. The data layer is the foundation of every upstream application and must be in place first.
  3. Search layer migration — ES → OpenSearch, run in parallel with the production database migration, neither blocking the other.
  4. Production microservice deployment + traffic cutover + external interface switch (unified window) — before T-day the cloud instances are deployed and pointed at the new production database (not yet taking traffic); in the T-day window: ① the gateway switches external traffic from the old physical machines to the cloud instances ② external systems update their call targets synchronously. Both are atomic.

3. Test Environment First: Microservice Containerization and Integration Validation

3.1 Why This Comes First

The whole migration touches multiple new variables at once: containerization, configuration center onboarding, cloud-side network policies, and K8s orchestration. Trial-and-error directly in production would be unacceptably costly. So the first thing we did after project kickoff was: run the full microservice-to-cloud flow once in the test environment, to confirm there was no structural flaw in the approach itself.

3.2 Work Done in the Test Environment

  • Containerization: adapted to K8s Deployment / StatefulSet, wrote the Dockerfile and deployment manifests.
  • Configuration center: connection strings, timeout parameters, and circuit-breaker rules were all centralized, pointing at an independent test database and test search cluster.
  • Network policies: security groups, whitelists, and dedicated-line connectivity between cloud-side Pods and the below-cloud database.
  • Logging and monitoring: integrated with the cloud platform’s logging service and APM.
  • End-to-end integration: verified that microservices on the cloud could correctly read from and write to the test database and test search cluster, and that business flows ran through.

3.3 Outputs of Successful Validation

Once the test environment validation passed, we had several key conclusions in hand:

  • Containerization was feasible; image builds and K8s deployment had no blocking issues.
  • The configuration center could correctly manage multi-environment parameters; switching environments required only a config change.
  • Connectivity, latency, and connection-pool behavior between cloud-side Pods and the below-cloud database all met production requirements.
  • Microservice compatibility with OpenSearch was confirmed (mappings, query syntax, aggregation behavior).

These conclusions gave the team confidence. Subsequent production migration followed the same path, with no lingering doubt about whether the approach itself would work.

4. Database Migration: RMAN Lays the Foundation, Data Guard Takes Over

4.1 Why Two Stages

The project adopted a “migrate the database first, migrate the applications later” phased strategy:

  1. The database data volume was in the terabytes; a one-shot outage would far exceed the maintenance window the bank would allow.
  2. Moving microservices to the cloud involved containerization and network policy adjustments, which take time.
  3. With the database in place first, the application side could fully test and integrate, reducing overall risk.

4.2 The Migration Plan Document and Review

After settling on the “RMAN + DG two-stage” technical route, I did not start working right away. Instead, I first wrote the 《Oracle Database Xinchuang Migration Operations Manual》, which became the sole basis for subsequent execution.

The document was required to be executable down to the command level:

Document Element Requirement Example
Time node Precise to the minute T-7 20:00 initiate level 0 full backup on the source DB
Execution server Identified by hostname/IP Execute on db-old-master (10.x.x.11)
Operation command Complete, copy-paste ready RMAN> BACKUP INCREMENTAL LEVEL 0...
Expected output What you should see after each command Finished backup at 2026-09-15 22:30
Verification step How to confirm this step succeeded SELECT * FROM V$BACKUP_SET; should show a new record
Exception handling What to do if a step fails If backup fails, check free space on the /backup mount point
Rollback step Rollback action if the migration is aborted at any stage Tear down the new standby; the old primary/standby architecture stays unchanged

Once the document was ready, a project team review meeting was called. Attendees included:

  • The client’s project manager
  • The DBA team (the executing party)
  • A representative from Operations (responsible for servers and network)
  • A representative from the Architecture Office (reviewing compliance of the plan)
  • A representative from the Security Office (reviewing whether the operation involved a security-affecting change)
  • The application-side owner (confirming the downtime window was acceptable)

The review went through the document line by line. Typical questions:

  • “Before the T-day switchover, does the final incremental backup’s archive coverage include all redo threads?”
  • “During new-standby recovery, will the source database’s archive-log cleanup policy delete archives that haven’t been shipped yet?”
  • “How long is the observation period, and can the old primary/standby carry the load of being promoted again during it?”

After revisions based on review feedback, the document was finalized, signed off by all parties, and filed with the change-management system. From then on, every operation was executed strictly by the document — no on-the-spot improvisation.

The point of this step: database migration is a high-risk operation. You cannot run it on the basis of “I remember how to do it.” Writing out every step as an executable command, having all sides review it, and getting sign-off both protects you and shows respect for the production environment.

4.3 The Source Already Had Primary/Standby; the New Server Joined as a Third Standby

6. Microservice Cloud Migration and External-Interface Coordinated Switchover

6.1 Why They Must Be Bound Together

Moving microservices to the cloud is not a standalone action. The entry address exposed by cloud-side microservices (gateway VIP / domain name) differs from that of the old physical-machine environment. This means the moment microservices cut over to the cloud, every external system’s call target must be updated at the same time. If microservices move to the cloud first and external interfaces switch later, external systems calling the old address fail for the whole intervening window; conversely, if external systems change their address first while microservices have not yet cut over, every call times out.

So microservice cloud migration and the external-interface switchover were merged into one coordinated operation within a single unified window: production deployment ready + gateway traffic switchover + external systems updating call targets synchronously, atomic.

6.2 Production Deployment and T-Day Traffic Cutover

Before T-day, the cloud-side production instances were fully deployed:

  • Image built, K8s resources created, configuration center pointed at the new production database.
  • Instances started up, but taking no external traffic (gateway weights kept all traffic on the old physical machines).
  • Internal health checks and connectivity verification completed.

Traffic cutover was executed in the T-day window — see section 6.8.

6.3 The Call-Relationship Matrix: Maintained Day to Day, Reused at the Critical Moment

The call-relationship matrix was something our team proactively maintained during day-to-day operations — recognizing early on that external-dependency grooming could not wait until migration kicked off. We continuously recorded each external system’s call direction, interface inventory, owner, and change history. Once this migration started, we simply filtered the matrix for every external system that called our interfaces, forming an initial list, then cross-validated it against gateway logs and firewall policies to confirm nothing was missed. The final count came to 14 external systems, covering core accounting, credit, mobile-banking back end, third-party payment, regulatory reporting, and the risk-control engine.

6.4 Producing the Plan and Reporting to the Client’s Project Manager

With the list in hand, I compiled a 《External Interface Coordinated Upgrade Plan》 and submitted it to the client’s project manager. It included:

Plan Item Content
Scope of impact List of 14 external systems + the interfaces called
Tiered classification Three classes A/B/C (config change only / code change required / re-integration testing required)
Timeline Back-scheduled: T-4 weeks preparation → T-1 week integration testing → T-day switchover
Owners per system Name + department + contact information
Risks and degradation plan Fallback for a single system failing
Approvals required Joint upgrade request, change ticket, director sign-off items

The core purpose of this plan was to make the scale and complexity visible to the client’s project manager, so they could get the authority to push other departments to cooperate.

6.5 Pushing the Approvals: Some Changes Need a Director’s Signature

In a bank, you cannot just change things because you say so. The 14 systems fell into three categories by type of change:

Class Count Change Required Approval Level
A: config change only 6 Change hosts / DNS / gateway upstream System owner approval
B: code change required 5 Hardcoded IP must be changed, then compiled, tested, released The other side’s release plan + test approval
C: re-integration required 3 Certificate reissuance, firewall change, contract adjustment Security-affecting change; director sign-off required

The approval flow was as follows:

flowchart TD
    A[We issue the Joint Upgrade Request Letter] --> B[Client project manager reviews and signs]
    B --> C{Has a security-affecting change?}
    C -->|Yes| D[Sent to the Information Security Office for review]
    D --> E[Information Security Office director signs]
    E --> F{Does it need the deputy head's signature?}
    F -->|Yes| G[Deputy head signs]
    F -->|No| H[Operations files it]
    G --> H
    C -->|No| H
    H --> I[Included in the joint change window]
    I --> J[Each external system starts internal dev/test against the signed document]

The hard part is queuing for the signature. A director’s sign-off goes to a meeting for discussion, requires a risk assessment, and must confirm it does not fall in a regulatory-inspection blackout period. From submitting a request to receiving approval, the fastest turnaround was five working days; some took one to two weeks. So the plan explicitly stated: the approval process must be started early — it cannot wait for the technology to be ready.

6.6 Issuing Formal Requests, Pushing System by System

Once framework-level agreement was secured, a formal letter was issued to each external system (via the bank’s internal OA plus a paper copy, run in parallel):

  • Letter content: the migration background, the new IP, the changes the other side needed to make, the deadline, and the contact person.
  • A written confirmation was required within five working days.
  • Classes B and C received an additional 《Interface Change Technical Specification》.

The purpose of this step was to leave a paper trail — in a bank, a verbal “yes” does not count; there must be written confirmation.

Actual feedback: 8 systems confirmed within 3 days; 4 asked for a delay (coordinated and rescheduled to the next window); 2 initially replied “cannot cooperate” (both ultimately agreed after the client’s project manager stepped in).

6.7 Integration Testing in the Test Environment

A test instance was deployed on the new servers, a test IP assigned, and each external system was verified one by one:

  • Class A: change the config, then call directly; verify the request arrives and the response is correct.
  • Class B: deploy the new version in the test environment after the code change, run the full business flow end to end.
  • Class C: reissue certificates + temporarily open the firewall + run the full interface-contract test.

An 《Integration Test Confirmation Form》 was produced, with each system signing off that “test-environment validation passed.”

The integration testing exposed two problems:

  • One system had a second hardcoded IP hidden in another part of its config file (they were unaware of it themselves).
  • One system’s firewall had port 80 open but not 443 — HTTP worked in the test environment, but HTTPS failed in production.

If those two traps had not been exposed in the test environment, they would have been incidents on T-day.

6.8 T-Day Execution: Production Deployment + Microservice Traffic Cutover + External-Interface Coordination

Of the 14 external systems, 12 passed on the first try; 1 had a missed config change (hot-fixed on site); 1 had an incomplete certificate chain (temporarily switched back to the old IP in read-only mode, fixed the next day).

6.9 Retrospective

Binding the microservice cloud migration and the external-interface switchover together was one of the most important lessons of this migration. Neither is technically complex — containerization is a mature approach, and changing a call address is trivial. But splitting them into two separate windows would have meant external-system call failures during any gap in between. Merging them into a single window doubled the coordination difficulty (getting external systems to change their addresses on the same night), but at least guaranteed the atomicity of the cutover.

Separately, all microservice refactoring and integration testing were done in the test environment; the production window only handled deployment and traffic cutover — which kept the T-day operation simple and predictable. The cloud instances were deployed and ready in advance but took no traffic; on T-day we only had to flip that one “switch” at the gateway, compressing the risk window to its shortest.

Getting 14 external systems to cooperate with you requires:

  • Foresight: the call-relationship matrix was maintained day to day and reused as soon as migration kicked off.
  • Planning first: lay out the scope, tiers, timeline, and approval needs, then get authorization from the project manager to push other departments.
  • Process awareness: security-affecting changes need a director’s signature and can queue for a week or two, so the approval process must start early.
  • Paper trails: formal letters, written confirmations, integration-test sign-offs — every step documented.
  • Testing discipline: even when the other side says “we only changed an IP,” the test environment must run it end to end.
  • Degradation and fallback: on cutover night there was a plan for “one system failing does not break the whole.”

One line sums it up: the technical plan took two weeks to settle; the coordination process ran six. In a bank migration, your technical ability determines whether you can move it; your coordination and process ability determine whether you finish.

Three core lessons:

  1. Test environment first — containerization, the configuration center, and network policies were all proven out in the test environment, confirming the approach had no hidden traps, before production migration began.
  2. Microservices and external interfaces must move together — once the external address changes, there is no such thing as “cut over halfway”; refactoring and integration testing happen in the test environment, while the production window only handles deployment and traffic cutover.
  3. Always keep a way back — at every stage, ensure the source side remains rollbackable.
