The Evolution of Concurrency Abstractions: From Paper Tape, Processes & Threads to Modern Coroutines

Jul 1 2024 Programming 15 minutes read (About 2185 words)

In the early days of computing, an operator would load a paper tape and the machine would run straight through from start to finish—unable to play music, print, or respond to the keyboard.
Today, in the era of high-performance servers and cloud-native computing, humanity’s pursuit of performance has reached near-extremes.

This article traces the evolution of concurrency abstractions from the 1950s to the present, focusing on the essential differences among processes, threads, fibers, and coroutines, as well as the design philosophy behind C++20 coroutines: “features, but no runtime.”

1. Concurrency Abstraction Timeline

Concept Earliest Idea / Term Emergence as a System Abstraction Notes
Program 1940s Always present Static code + data; not an execution state
Job 1950s batch processing IBM 7090 / OS/360 era “A batch of work to run”; not a modern process
Task 1960s Used inconsistently across systems Sometimes ≈ process, sometimes ≈ thread
Coroutine Coined by Conway in 1958; paper in 1963 Simula 67, Modula-2, Lua, Python, Go User-space, cooperative control flow
Process Mid-1960s Formally proposed in Multics (1965–69); solidified in UNIX in 1969 Born from multiprogramming / time-sharing
Thread 1960s–70s concurrency research Research systems in the 1980s; mainstream in the 1990s (Solaris, Win NT 3.1, POSIX pthreads 1995) Concurrent execution flow within a process
User-level thread / green thread 1970s–80s Java 1.1 green threads, Scheduler Activations 1991 “Threads” invisible to the kernel
Fiber Idea rooted in coroutines / user-level threads Officially named Fiber in Windows NT 3.51 SP (1996) Cooperative context within a thread
Modern async/await coroutine 2000s–2010s C# 2012, Python 3.5, JS ES2017, Rust, C++20, Java Virtual Threads 2023+ The “triumphant return” of the coroutine idea

2. Process: The Unit of Resource Allocation

2.1 Essence

A process is an instance of a program in execution on a certain data set, and is the basic unit by which the OS performs resource allocation and scheduling. It is not a bare program, but rather a snapshot of all resources needed to run:

  • Program code (Text segment)
  • Data segment (global / static variables)
  • Heap (dynamically allocated memory)
  • Stack (function calls, local variables)
  • Process Control Block (PCB) — the core data structure the OS uses to manage processes; without a PCB, the kernel “doesn’t recognize” the process

The PCB stores the process’s identity and execution context:

  • PID
  • Process state (running, ready, blocked)
  • Program counter (address of the next instruction)
  • CPU register values
  • Memory management information
  • List of open files
  • Scheduling information

2.2 Core Characteristics

✔ Resource container: A process has its own independent virtual address space, file handles, signal handlers, etc. Resource isolation is thorough—when one process crashes, it generally does not affect other processes on the same machine.
✔ Scheduling unit: In traditional time-sharing OSes, the process is the basic unit of CPU allocation.
✔ Relatively high overhead: Creation, destruction, and switching all require kernel intervention, involving memory mapping and PCB operations, at millisecond-level cost.

2.3 Typical Problems

✘ High switching cost: Context switching requires saving/restoring the entire address space, with TLB flushes and cache invalidation; frequent switching wastes a lot of CPU.
✘ Complex communication: Inter-process communication (IPC) must rely on pipes, message queues, shared memory, etc.—clumsier than thread-to-thread communication.
✘ Limited quantity: A single machine hits a bottleneck at a few thousand processes, and cannot easily support the hundreds of thousands of concurrent entities that threads and coroutines can.

3. Thread: The Execution Unit Scheduled by the Kernel

3.1 Essence

A thread is the smallest unit the OS can schedule. It exists attached to a process, sharing the address space and file handles, but has its own stack, registers, and TLS.

Process = resource container; Thread = execution flow

3.2 Kernel Threads vs. User Threads

Type Description
Kernel Thread (KLT) Managed by the OS kernel; scheduling, switching, and synchronization are all handled by the kernel
User Thread (ULT) Implemented entirely in user space; invisible to the kernel

Modern mainstream languages (Java, std::thread, Rust) basically use the 1:1 model: one user thread maps to one kernel thread.

3.3 Core Characteristics and Problems

✔ Preemptive scheduling (forced switching via time slices / priorities)
✔ Hardware context switching (privilege-level switch, TLB flush, cache invalidation)
✘ High cost: creation / destruction / switching overhead is at the microsecond level
✘ Limited quantity: a single machine hits a bottleneck at a few thousand threads

Too many threads, frequent context switches, and the CPU spending most of its time switching rather than computing — this is precisely the root cause driving the search for lighter-weight models in the C10K and C10M problems.

4. Fiber: A User-Space “Lightweight Thread”

4.1 Essence

A fiber is a cooperatively scheduled execution unit implemented entirely in user space. It is not part of the POSIX standard, and is found in the Windows Fiber API and Boost.Fiber.

Fiber ≈ user-space thread + cooperative scheduling

4.2 Core Characteristics

Feature Description
Scheduling Cooperative: yields actively, is not preempted
Switching cost Extremely low: only saves/restores registers + stack pointer (nanosecond level)
Quantity Can easily create hundreds of thousands or even millions
Kernel awareness None — the kernel only knows the underlying thread

Key clarification: a fiber must be parasitic on a thread.

  • One thread can schedule N fibers
  • At any given moment, a thread can run only one fiber
  • The thread itself is still preemptively scheduled by the kernel

4.3 Typical Implementations and Fatal Flaw

  • Windows Fiber API: ConvertThreadToFiber, SwitchToFiber
  • Boost.Fiber (based on boost::context)

⚠️ An infinite loop in one fiber = the entire thread freezes. Because there is no preemption, if one fiber does not yield, the other fibers on the same thread will never get to run.

5. Coroutine: Language-Level Cooperative Multitasking

5.1 Essence

A coroutine is a function that can be suspended during execution and resumed afterward. It is not an OS concept, but rather an abstraction at the language/library level.

Coroutine = state machine + suspend/resume semantics

Another point that must be clarified: a coroutine ultimately also runs on a thread — without a thread, a coroutine simply cannot run. It merely moves the “scheduling authority” from the kernel to user space / the language runtime.

5.2 Coroutine Classifications

By control-transfer style:

Type Description Representative
Symmetric coroutine Any coroutine can switch to any other Modula-2
Asymmetric coroutine Can only return to its caller C++20, Python, Kotlin

By stack form:

Type Description Representative
Stackful coroutine Each coroutine has its own stack Go goroutine, Lua
Stackless coroutine State stored on the heap, reuses the call stack C++20 co_await, Rust async

5.3 Comprehensive Four-Way Comparison

Dimension Thread Fiber Coroutine
Scheduler Kernel User library Language runtime
Switching style Preemptive Cooperative Cooperative
Stack size MB level KB~MB Stackless or small stack
Scale Thousands Hundreds of thousands to millions Hundreds of thousands to millions
Cost of blocking High Low Low
Execution carrier Itself Thread Thread

5.4 Language Implementation Comparison

Go: goroutine + GMP scheduling

Stackful coroutine (initial 2KB, dynamically grows/shrinks); GMP model G - M - P; network poller + preemption support after 1.14.

Python: async/await

Driven by an event loop, with cooperative switching within a single thread.

C++20: stackless coroutine

A state machine generated at compile time, with zero extra stack overhead; the standard provides no scheduler, thread pool, or event loop.

6. An In-Depth Look at C++20 Coroutines: Features, but No Runtime

6.1 What the Standard Provides

C++20 wrote coroutines into the standard: co_await / co_yield / co_return + coroutine_handle + the promise mechanism.

But the standard does not provide: a thread pool, an event loop, a default scheduler, asynchronous sockets, or automatic M:N scheduling.

The C++ philosophy: “I give you coroutine primitives; I don’t decide how you do concurrency.”

6.2 Status by Version

Version Coroutine Syntax Coroutine Runtime
C++17 and earlier ✘ ✘ (rely on third-party libraries)
C++20 ✔ ✘
C++23 ✔ + std::generator ✘
C++26 (in progress) ✔ + parts of std::execution Executor abstraction, not a complete runtime

Comparison with other languages:

Language Lightweight concurrency unit Built-in runtime
Go goroutine ✔ GMP + netpoller
Java 21+ Virtual Thread ✔ JVM + ForkJoinPool
Kotlin coroutine ✔ runtime + Dispatcher
C# / .NET async Task ✔ CLR + Task Scheduler
C++20/23 coroutine ✘ at the standard level

6.3 Why Coroutines Must Run on a Thread

C++20 uses stackless coroutines: the coroutine frame lives on the heap, and when resumed it borrows the caller thread’s stack to execute.

foo() only creates the coroutine frame; when it runs and on which thread is entirely up to you (or your library) and how you call resume().

coroutine_handle::resume() necessarily happens inside some thread.

6.4 The Timing of Coroutine Suspension / Resumption

sequenceDiagram
    participant Caller as Caller Thread
    participant Coro as Coroutine Frame (heap)
    participant Awaiter as Awaiter
    participant Pool as Thread Pool (worker)

    Caller->>Coro: call foo(), create coroutine frame
    Caller->>Coro: co_await x, suspend
    Coro->>Awaiter: call await_suspend(h)
    Awaiter->>Pool: post handle to task queue
    Caller-->>Caller: caller thread returns immediately (non-blocking)
    Pool->>Pool: worker takes task
    Pool->>Coro: h.resume() on some worker thread
    Coro->>Caller: coroutine continues until next suspension point

Core conclusion: The real meaning of co_await x is — “I am suspending now; which thread wakes me up later is decided by x.await_suspend().” A coroutine does not run “somewhere else”; it runs on the thread that calls resume(). The thread pool is not part of the coroutine — it is the scheduling backend of the awaiter.

8. Differences in Design Philosophy

8.1 Scheduling Philosophy

  • Thread: You never know when you’ll be switched out — you must lock everywhere
  • Fiber / coroutine: Switching happens only at yield/await points — no locks needed for critical sections within a single thread

8.2 Concurrency vs. Parallelism

  • Thread: Naturally supports parallelism (multi-core)
  • Fiber / coroutine: Essentially concurrent; parallelism depends on being bound to multiple threads

A coroutine not blocking a thread ≠ a coroutine not needing a thread

8.3 One-Liner to Distinguish the Three

A thread is the OS’s abstraction, a fiber is the user’s attempt, and a coroutine is the language’s answer.

A Go programmer writing coroutines is using a runtime; a C++ programmer writing coroutines is building a runtime.

10. Summary

  • Threads solved the problem of parallelism, but at a high cost
  • Fibers proved the feasibility of user-space scheduling, but cooperative scheduling has its limits
  • Coroutines, through language-level support, turn asynchronous code into something that looks synchronous, greatly reducing mental burden
  • C++20 provides coroutine primitives but no runtime, leaving scheduling freedom to the developer

A thread is the OS’s unit of execution; fibers and coroutines are user-space execution flows. They do not replace threads — they are built on top of threads, organizing concurrency in a lighter-weight way.
