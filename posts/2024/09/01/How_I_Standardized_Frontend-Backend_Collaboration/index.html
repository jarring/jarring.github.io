How I Standardized Frontend-Backend Collaboration as a Tech Lead

Sep 1 2024 TechLeadership 14 minutes read (About 2028 words)

Tired of broken client demos and last-minute integration chaos? Here’s how I used Swagger + Apifox + local Mock to build a contract-driven workflow that lets frontend and backend ship in parallel — and demo the system offline, anytime.

1. Background: Why We Needed a Process

Serveral years ago, our team had a classic pre-release incident: on launch eve, the frontend team discovered that several API response structures had changed silently. Pages broke. Emergency fixes followed. Blame was exchanged.

The root cause was not technical — it was process debt:

  • Interfaces were discussed verbally, never documented formally
  • Changes were made without notification
  • Frontend had no way to develop independently
  • “It works on my machine” was the default acceptance criteria

As the tech lead, I realized: collaboration cannot rely on personal memory or good intentions. It must rely on mechanism.

This article describes the workflow, toolchain, and team norms I established to fix this permanently.

4. Core Toolchain

4.1 Swagger / springdoc-openapi — The Contract Center

We adopted springdoc-openapi (official: https://springdoc.org/) to auto-generate OpenAPI 3 specs from Spring Boot applications at runtime.

Key decisions:

  • /v3/api-docs is the Single Source of Truth for all interface definitions
  • Every endpoint must have Swagger 3 annotations (io.swagger.v3.oas.annotations)
  • DTOs must include @Schema(description = "...", example = "...") — these examples drive Mock data generation
  • Direct database entity exposure is prohibited; DTO/VO layers are mandatory

Starting the Spring Boot app automatically deploys:

  • OpenAPI JSON: http://server:port/v3/api-docs
  • Swagger UI: http://server:port/swagger-ui.html

4.2 Apifox — Documentation + Remote Mock

We use Apifox (https://apifox.com/) as the team’s unified API collaboration platform.

Process:

  1. Backend starts Spring Boot → generates /v3/api-docs
  2. Import URL into Apifox → auto-generates interactive docs + Mock endpoints
  3. Frontend uses Apifox Mock URLs for development before backend is ready

This eliminates handwritten mock data and ensures frontend development is always based on the real contract, not assumptions.

4.3 Local Mock — Zero-Dependency Development

For scenarios where the network is unstable or Apifox is unreachable, we use a Vite middleware that intercepts /api requests and returns local JSON files. No extra process, no port, zero dependencies.

6. Demo-Ready at Any Time — A Pain Point Solved

This is a benefit I didn’t anticipate when introducing the mock setup, but it quickly became one of its highest-value outcomes.

The Old Pain

Before this process, demonstrating the system to clients was a high-stress event:

  • Backend must be deployed and running — if the server was down, demo was dead
  • Database must contain realistic seed data — no data = empty tables = unimpressive
  • Network must be stable — client site WiFi, VPN drops, firewall blocks all meant “sorry, let me retry”
  • Timing dependency — you couldn’t promise a demo date without backend being ready
  • The “it worked yesterday” moment — backend restart, DB reset, or a silent code change could break the demo minutes before the meeting

I’ve been in that room. You open the laptop, the client leans in, the spinner spins… and you say “let me check something.” The credibility damage is real.

The New Reality

With VITE_API_MODE=mock, the frontend build runs entirely offline. No backend, no database, no internet. The mock middleware serves curated JSON files instantly.

Scenario Before After
Backend down during demo ❌ Demo fails, awkward silence ✔ Mock serves instantly
Client site has bad WiFi ❌ API calls timeout ✔ Fully offline, zero network
Need specific data state (empty cart, error page, 50-item list) ❌ Must seed DB manually, hope nothing breaks ✔ Swap one JSON file
Pre-sales pitch, backend not started ❌ Wait 2–3 weeks for backend MVP ✔ Frontend alone is presentable
Client asks “can you show X?” on the spot ❌ X might not exist in DB ✔ Pre-crafted mock covers every flow

How We Manage It

As tech lead, I established one simple rule:

Mock data used for demos must be curated. Clean, realistic, covering key user journeys. We keep a mock/demo/ directory separate from dev mocks, with hand-picked data that tells a good story.

This means:

  • mock/dev/ — rough data for daily development, can be messy
  • mock/demo/ — polished fixtures: 10 users with real names, 5 orders in different states, proper pagination, deliberate error cases

During client meetings, we build a demo mode that loads from mock/demo/. The PM and I align beforehand on which flows to showcase, and the mock data is prepared to make those flows look smooth.

The Management Upside

This changes the dynamics of client communication:

  1. You can promise demo dates without being blocked by backend进度. The frontend becomes independently presentable.
  2. Sales/pre-sales cycles shorten. You don’t wait for “backend ready” to start showing the product.
  3. Client confidence increases. A smooth, offline-capable demo signals professionalism — “this team has their act together.”
  4. No more demo anxiety. You walk into the room knowing the system will work regardless of the environment.

One of our PMs put it best: “I used to dread demo days. Now I actually look forward to them.”

7. Change Management — The Rules

flowchart TD
    A[API Change Needed] --> B{Change Type?}
    B -->|Additive / Non-breaking| C[Backend updates Swagger annotations directly]
    B -->|Breaking change<br/>field removed/renamed| D[Initiate Change Review]
    D --> E[Notify frontend to assess impact]
    E --> F{Frontend affected?}
    F -->|Yes| G[Coordinate timeline, sync code changes]
    F -->|No| H[Proceed with change]

    C --> I[Regenerate /v3/api-docs]
    G --> I
    H --> I
    I --> J[Re-import Apifox]
    J --> K[Announce change to team]
    K --> L[Code Review verifies annotation completeness]

    style B fill:#fffbe6,stroke:#faad14
    style D fill:#fff1f0,stroke:#f5222d
    style L fill:#f6ffed,stroke:#52c41a

Rules I established as tech lead:

  1. No silent changes — any interface modification must update Swagger annotations
  2. Breaking changes require review — removing or renaming fields needs frontend sign-off
  3. Documentation is part of the Definition of Done — PRs without Swagger annotations are rejected in Code Review
  4. Apifox sync is mandatory — after every annotation change, re-import into Apifox and notify the team

    I --> K
    J --> K
    K --> L{Resolved?}

Frontend must report issues using a standard template:

  • Request URL
  • Request parameters (body/query)
  • Expected vs actual response
  • Screenshot or screen recording

This eliminates “it doesn’t work” tickets and cuts debugging time by ~60%.

10. Summary

As a tech lead, your job is not to write the most code. It is to build systems that prevent errors, reduce waste, and make team output predictable.

The combination of Swagger (contract) + Apifox (collaboration) + Local Mock (independence) + Process rules (governance) gave us:

  • ✔ Frontend and backend work in parallel without blocking each other
  • ✔ Interface changes are visible, reviewable, and traceable
  • ✔ New team members onboard in hours, not days
  • ✔ Production bugs from interface mismatches dropped dramatically
  • ✔ Client demos are no longer at the mercy of backend readiness

The best process is the one your team actually follows. Start simple, enforce consistently, and iterate.
